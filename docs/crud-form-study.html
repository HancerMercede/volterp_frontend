1 Arquitectura General

🎯 Concepto central

useCrudForm es un hook genérico que centraliza todo el estado y la lógica de formularios CRUD (valores, errores, submit, edición). DynamicFormFields es un componente puro que recibe ese estado y renderiza los campos según la configuración declarativa FormField[]. Juntos eliminan el boilerplate repetido en las 7 páginas CRUD del sistema.

Separación de responsabilidades

ComponenteRenderizado de campos según FormField.typeDynamicFormFields.tsx
PáginaConfigura los fields, conecta stores, orquesta modalesClientes.tsx (ejemplo)

💡 Clave: El hook NO renderiza nada. El componente NO tiene estado de formulario. La página solo configura y orquesta. Cada uno hace una cosa y la hace bien.

2 Sistema de Tipos

Todo arranca con tres interfaces que forman el contrato público del hook. Son genéricas (<T extends Record<string, unknown>>) para adaptarse a cualquier entidad del dominio.

FormField — la configuración declarativa

// Cada objeto = un campo del formulario
export interface FormField {
  name: string;              // key en el objeto values
  label: string;             // texto visible
  type: "text" | "email" | "tel" | "number"
       | "select" | "date" | "file"
       | "checkbox" | "url";

  required?: boolean;         // valida que no esté vacío
  placeholder?: string;

  // Para <select>
  options?: { value: string; label: string }[];

  // Visibilidad contextual
  showOnEdit?: boolean;   // solo en edición (ej: isActive)
  showOnCreate?: boolean; // solo en creación

  // Passthrough a <input> + validación JS
  min?: number;
  max?: number;
  minLength?: number;
  maxLength?: number;
  step?: number;

  // Para type: "file" — default "image/*"
  accept?: string;

  // Validador custom: recibe (value, allValues)
  validate?: ValidateFn;
}

🎭 Discriminación por type

type es un string literal union de 9 valores. Cada valor dispara un renderer distinto en DynamicFormFields y un validador diferente en el hook. TypeScript fuerza a cubrir todos los casos.

🧩 Visibilidad contextual

showOnEdit / showOnCreate permiten que el mismo array de fields tenga comportamiento distinto según el modo. Ej: isActive solo tiene sentido al editar.

🔌 Passthrough + validación dual

Props como min/max son tanto atributos HTML (<input min={x}>) como parámetros de validación JS. Como handleSubmit hace e.preventDefault(), la validación nativa del browser no corre → necesitamos la JS.

🔧 validate custom

Función que recibe el valor y todos los valores del form. Permite validaciones complejas: confirmar password, rangos cruzados, etc. Siempre se ejecuta al final de la pipeline.

CrudFormConfig — la configuración del hook

export interface CrudFormConfig<T extends Record<string, unknown>> {
  fields: FormField[];           // definición declarativa
  defaultValues: T;              // valores iniciales + template
  onCreate: (data: T) => Promise<unknown>;  // POST
  onUpdate: (id: number, data: T) => Promise<unknown>;  // PUT
  onSuccess?: () => void;         // callback post-submit exitoso
  mapEntityToForm?: (entity: Record<string, unknown>) => T;
}
📌 defaultValues tiene doble propósito: (1) valores iniciales del formulario, (2) template para pickKeys() — cuando se edita, solo se extraen del objeto fuente las keys que existen en defaultValues. Esto evita que propiedades extrañas de la entidad contaminen el form.

CrudFormReturn — lo que el hook expone

export interface CrudFormReturn<T> {
  values: T;                                   // estado actual del form
  errors: Record<string, string>;           // { fieldName: mensaje }
  isSubmitting: boolean;                     // loading state
  submitError: string | null;               // error del API call
  editingId: number | null;                  // null = create, number = update
  setFieldValue: (name: string, value: unknown) => void;
  handleSubmit: (e: React.FormEvent) => Promise<void>;
  handleEdit: (entity: object, id: number) => void;
  reset: () => void;
}

3 Anatomía del Hook

Estado interno

const [values,      setValues]      = useState<T>({ ...defaultValues });
const [errors,      setErrors]      = useState<Record<string, string>>({});
const [isSubmitting, setIsSubmitting] = useState(false);
const [submitError,  setSubmitError]  = useState<string | null>(null);
const [editingId,   setEditingId]   = useState<number | null>(null);
EstadoTipoFunción

errorsRecord<string, string>Mapa fieldName → mensaje. Se limpia por campo al editar.
isSubmittingbooleanIndica si hay una operación asíncrona en curso. Deshabilita botones.
submitErrorstring | nullError capturado del catch del API call. Se limpia al tocar cualquier campo.

setFieldValue

const setFieldValue = useCallback((name: string, value: unknown) => {
  setValues((prev) => ({ ...prev, [name]: value }));
  setErrors((prev) => {
    if (!(name in prev)) return prev;         // no había error → no crear objeto nuevo
    const next = { ...prev };
    delete next[name];                         // limpia el error de ese campo
    return next;
  });
  setSubmitError(null);                          // el usuario ya está corrigiendo
}, []);
🔑 Optimización: setErrors solo crea un nuevo objeto si el campo tenía error. Si no había error, retorna el mismo objeto (React no re-renderiza si la referencia no cambia).

handleEdit

const handleEdit = useCallback(
  (entity: object, id: number) => {
    const dict = entity as Record<string, unknown>;
    const mapped = mapEntityToForm
      ? mapEntityToForm(dict)
      : pickKeys(defaultValues, dict);
    setValues(mapped);
    setEditingId(id);
    setErrors({});
    setSubmitError(null);    // estado limpio para editar
  },
  [defaultValues, mapEntityToForm],
);
📌 pickKeys() — Mapper por defecto: Toma la entidad fuente y extrae solo las keys que existen en defaultValues. Esto permite que una entidad con 20 propiedades solo cargue en el form las 5 que definen los fields. El mapper custom (mapEntityToForm) permite transformaciones: fechas, enum→string, etc.

handleSubmit — el ciclo completo

const handleSubmit = useCallback(
  async (e: React.FormEvent) => {
    e.preventDefault();                          // ❌ mata validación nativa

    const validationErrors = validateForm(fields, values);
    if (Object.keys(validationErrors).length > 0) {
      setErrors(validationErrors);               // muestra errores
      return;                                       // corta aquí
    }

    setIsSubmitting(true);
    setSubmitError(null);

    try {
      if (editingId !== null) {
        await onUpdate(editingId, values);           // PUT
      } else {
        await onCreate(values);                        // POST
      }
      reset();                                        // limpia todo
      onSuccess?.();                                 "> callback
    } catch (err) {
      setSubmitError(err instanceof Error
        ? err.message
        : "Error al guardar");
    } finally {
      setIsSubmitting(false);
    }
  },
  [fields, values, defaultValues, onCreate, onUpdate, onSuccess],
);
⚠️ e.preventDefault() valida invisible: Al prevenir el submit nativo del browser, también prevenimos checkValidity() del HTML5. Por eso toda la validación (min, max, step, email, etc.) se implementa en JavaScript. El hook es 100% responsable de la validación.

4 Sistema de Validación

El sistema de validación usa un patrón de validator dispatch por tipo con una pipeline de 4 capas. Cada capa puede retornar un error o undefined (sigue con la siguiente).

🔬 Pattern Matching simulado

TypeScript no tiene match como Rust. La alternativa es un mapa Partial<Record<FormField["type"], Validator>> donde la key es el discriminante y el valor es la función validadora. Se resuelve con typeValidators[field.type]?.(...).

Pipeline de validación

1Required — Si field.required y el valor está vacío → error. Corta aquí.
2Type validator — Busca typeValidators[field.type], lo ejecuta. Si hay error, corta.
3String constraints — Si el valor es string, verifica minLength / maxLength.
4Custom validator — Ejecuta field.validate?.(value, values).

typeValidators — el mapa de dispatch

type Validator = (
  field: FormField,
  value: unknown,
  values: Record<string, unknown>
) => string | undefined;

const typeValidators: Partial<Record<FormField["type"], Validator>> = {
  // ── Email ──
  email: (f, v) =>
    typeof v === "string" && v && !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v)
      ? "Email inválido"
      : undefined,

  // ── Number (min, max, step) ──
  number: (f, v) => {
    if (typeof v !== "number" || isNaN(v)) return;
    if (f.min !== undefined && v < f.min)
      return `${f.label} debe ser mayor o igual a ${f.min}`;
    if (f.max !== undefined && v > f.max)
      return `${f.label} debe ser menor o igual a ${f.max}`;
    if (f.step !== undefined && f.step > 0) {
      const diff = Math.abs((v - (f.min ?? 0)) % f.step);
      if (diff > 1e-8)
        return `${f.label} debe ser múltiplo de ${f.step}`;
    }
  },

  // ── File (MIME type validation) ──
  file: (f, v) => {
    if (typeof v !== "string" || !v.startsWith("data:")
      || !f.accept || f.accept === "*") return;
    const mime = v.split(";")[0].split(":")[1];
    const ok = f.accept.split(",").map((a) => a.trim()).some((a) =>
      a.endsWith("/*")
        ? mime.startsWith(a.replace("/*", ""))
        : a === mime
    );
    if (!ok) return `Formato de archivo no válido. Permitidos: ${f.accept}`;
  },
};

🎯 Partial<Record<...>>

No todos los tipos necesitan validador (text, tel, date, checkbox, url no tienen entrada en el mapa). Partial permite keys opcionales y ?. al invocar.

📐 Validación de step con floats

(v - base) % step puede dar 0.000000001 por precisión de floats. El epsilon 1e-8 tolera esos errores mínimos sin falsos positivos.

🖼️ File accept desde data URL

El FileReader convierte la imagen a base64: data:image/png;base64,.... Extraemos el MIME (image/png) y lo comparamos contra accept. Solo valida si el valor es data URL (no URLs existentes en edición).

🔗 validateForm

Itera el array de fields ejecutando validateFielduno por uno y recolecta errores en un Record<fieldName, message>.

5 DynamicFormFields — Renderizado

Componente puro y no-controlado visualmente: recibe values y onChange del hook, nunca tiene estado interno de formulario. Solo FileField tiene estado local (nombre de archivo, drag state) porque es UI efímera que no persiste.

Props

interface Props {
  fields: FormField[];           // definición de campos
  values: Record<string, unknown>;  // del hook
  errors: Record<string, string>;  // del hook
  editingId: number | null;       "> modo create/edit
  onChange: (name: string, value: unknown) => void;  // setFieldValue
}

Estructura de renderizado

export function DynamicFormFields(props: Props) {
  return (
    <div className={styles.fields}>
      {props.fields.map((field) => {
        // Filtro de visibilidad
        if (field.showOnEdit && editingId === null) return null;
        if (field.showOnCreate && editingId !== null) return null;

        return (
          <FieldRenderer
            field={field}
            value={values[field.name]}
            error={errors[field.name]}
            onChange={onChange}
          />
        );
      })}
    </div>
  );
}

FieldRenderer — dispatch por tipo

El renderer usa early returns con if (field.type === "select"). Esto es equivalente al patrón match de otros lenguajes — cada tipo retorna su JSX y corta. El orden importa: select, checkbox y file se manejan antes que el default input genérico.

1select → <select> con options y placeholder default "Seleccionar {label}"
2checkbox → <input type="checkbox"> con checked={Boolean(value)}
3file → <FileField> con drop zone, preview, drag & drop
4number → <input type="number"> con parse especial (int vs float según step)
5default → <input type={field.type}> para text, email, tel, date, url
🔧 Number parsing: Cuando step < 1 (decimales), usa parseFloat(e.target.value) || 0. Caso contrario, parseInt(...) || 0. Esto evita que "" o "e" se conviertan en NaN.

8 Resumen & Decisiones

🧠 Síntesis del patrón

useCrudForm es un hook genérico con tipado seguro que elimina el boilerplate CRUD mediante una configuración declarativa. DynamicFormFields es el componente que traduce esa configuración a UI. Juntos forman un motor de formularios liviano con 0 dependencias externas.

Decisiones arquitectónicas clave

DecisiónAlternativa descartadaPor qué
Hook + Componente separados Un solo componente todo-en-uno El hook puede testearse en aislamiento. El componente puede reemplazarse (ej: mobile vs desktop). Separación de responsabilidades.
Partial<Record<T["type"], Validator>> if/else chain o switch Más declarativo, fácil de extender (solo agregás una entrada al map), TypeScript fuerza a tipar bien la key. El if chain original mezclaba formatos, rangos y string constraints.
FileReader en el componente FileReader en el hook El hook no debe saber de DOM ni de File API. El componente maneja la conversión a base64 y pasa el string al hook.
defaultValues como template + pickKeys Mapeo manual entidad → form El mapper por defecto (pickKeys) cubre el 90% de los casos. Para el 10% restante existe mapEntityToForm. No obligamos a escribir un mapper siempre.
submitError se limpia en setFieldValue Solo se limpia al hacer submit UX: si falló el submit y el usuario empieza a escribir, el error debe desaparecer. Si no, el usuario asume que el sistema está trabado.
Validación JS de min/max/step Confiar en validación HTML5 nativa e.preventDefault() en handleSubmit cancela checkValidity(). No podemos confiar en la validación del browser. Toda validación corre en JavaScript.
Partial<CrudFormConfig> y Partial<T> para updates Tipos Create/Update separados Request = Partial<Dto> unifica Create y Update. El form siempre envía el objeto completo, el backend ignora lo que no necesita.

Principios que sigue este patrón

🎯 Single Responsibility

El hook maneja estado y lógica. El componente renderiza. La página configura y orquesta.

🔒 Type Safety

Genéricos <T> en todo el pipeline, discriminación por type, validate tipado.

⚡ Performance

useCallback, useMemo, reference equality checks, evitar re-renders innecesarios.

🧪 Testeable

El hook es puro (recibe config, devuelve state + callbacks). Sin DOM, sin side effects externos.

🧩 Extensible

Agregar un nuevo type: (1) agregarlo al union type, (2) agregar validador al map, (3) agregar renderer en FieldRenderer.

📦 Zero deps

0 dependencias externas de formularios. Solo React + i18n para textos. Control total del comportamiento.
